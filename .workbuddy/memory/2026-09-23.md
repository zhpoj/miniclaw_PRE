## miniclaw_PRE — 打通「飞书消息 → agent run」（IM 第 1 步）

### 现状
- 上一轮（09-22）只落地了 IM 层骨架：`src/im/IMChannel.ts` 契约 + `src/im/feishu.ts` 适配器（tenant token、X-Lark 签名、AES 解密、webhook 解析）+ `mountIMChannels`。
- 本轮补的是"接住消息之后干什么"：`src/im/bridge.ts` 的 `IMBridge`。

### 关键设计决策（下次继续按这个走）
- **绑定粒度**：`channelId:conversationId` → 一个 `AgentRun`，一个群/单聊 = 一份会话上下文上限靠 `IM_MAX_CONVERSATIONS`(50) + LRU 淘汰。
- **webhook 必须秒回**：飞书约 1s 判投递失败 → `bridge.handle()` 只接住+入队立刻返回，回合后台跑完再回。`attach(channel)` 内部订阅时用 `void this.handle()`。
- **回合串行 + 有界队列**：`IM_MAX_QUEUE`(3)，满则回"队列也满了"；回合结束 `drain()` 自动跑下一条。
- **答案抽取**：订阅 run 事件，`message_end` 取 assistant 完整文本为主，`message_update` 的 `text_delta` 兜底（超时/中断仍有半截内容）。
- **依赖收窄以便测试**：`IMBridgeEngine = Pick<AgentEngine,'createRun'>`、`IMRun = Pick<AgentRun, id|snapshot|prompt|awaitIdle|subscribe|abort|close>`，测试用 fake，不碰真模型。
- 环境变量统一前缀 `IM_*`（`IM_TURN_TIMEOUT_MS`/`IM_MAX_QUEUE`/`IM_MAX_CONVERSATIONS`/`IM_STREAMING`/`IM_STREAM_INTERVAL_MS`/`IM_MAX_REPLY_CHARS`），飞书端 `FEISHU_*`。

### 验证方式（可复用）
- `node test_feishu.mjs`：起本地假飞书开放平台(8799，mock tenant token + 发消息 + 改消息)，服务把 `FEISHU_BASE_URL` 指过去，投一条 `im.message.receive_v1`，断言真的收到回复。真模型 ~10s 出结果。
- 加 `--stream` 走流式卡片回填分支。
- 单测：`npx vitest run`（44 项），`npx tsc --noEmit` + `npm run build`。
